审核与上架流程

这是一个纯静态站点（GitHub Pages）。路人提交的数据会通过表单服务发送到维护者邮箱； 维护者人工核对后，把通过的文字信息写入 data/manga-data.js 并部署，全站自动更新。

第 1 步 · 配置数据提交通道（首次必做）

打开 data/config.js，选择一种后端：

方案 A：GitHub Issue（不暴露任何 Token，当前默认，推荐）

  1. 在 GitHub 仓库中先创建三个标签：submission、pending、approved。
  2. 把 feedback.backend 设为 "githubIssue"。
  3. 把仓库填入 feedback.githubIssueRepo，格式为 拥有者/仓库名。
  4. 可自定义 feedback.githubIssueLabels，默认 ["submission", "pending"]。

访客提交数据时，前端会把表单内容整理成 Issue 标题和正文，并弹出确认框；访客点击「前往 GitHub 提交 Issue」后，在新 Issue 页面里手动拖入佐证图片并点击 Submit new issue。此流程不需要任何 Token 或后端服务。

方案 B：Web3Forms（发送到邮箱）

  1. 访问 web3forms.com，用邮箱领取 Access Key。
  2. 把 feedback.backend 改为 "web3forms"，并把 Key 填入 feedback.web3formsAccessKey。

方案 C：Formspree（发送到邮箱）

  1. 在 formspree.io 创建表单，得到 https://formspree.io/f/xxxx。
  2. 把 feedback.backend 改为 "formspree"，并把地址填入 feedback.formspreeEndpoint。

配置完成后，数据提交页的提交按钮会自动启用。

第 2 步 · 审核提交数据

  • GitHub Issue 模式：会收到带 submission 和 pending 标签的 Issue，标题为 [投稿] …，正文是整理好的表单内容。审核时在 GitHub 上把标签 pending 改为 approved 并关闭 Issue。
  • 邮箱模式：邮箱里会收到主题为 [KIGUBI数据] … 的邮件，含数据类型（新增/修改）、漫画、章节色块状态、修改原因和佐证图片（每张带章节备注）。
  • 核对漫画、章节与描述是否准确；佐证图片只用于核对，不对外。
  • 无法确认的条目直接忽略；确认无误后进入第 3 步。

第 3 步 · 写入数据

打开 data/manga-data.js，按现有结构插入记录。

// 已有漫画：在对应 chapter 的 kiss 或 nudity 数组中追加
{
  characters: "角色 A × 角色 B",
  note: "场景与镜头的一句话描述（不要出现图片外链或资源链接）。"
}

如果漫画尚未收录，复制一个完整的漫画对象，替换 slug（英文唯一）、cover（封面图可放 assets/covers/）和章节信息。

第 4 步 · 部署

  • 推送到 GitHub 仓库的 main 分支（或你设置了 GitHub Pages 的分支）。
  • GitHub Pages 构建完成后，首页与详情页自动显示新条目。

首页筛选与章节模式说明

  • 首页左侧的“条件筛选”支持：连载中 / 有亲吻 / 有露点，可多选叠加。
  • 详情页默认使用折叠模式：每个章节只显示一个数字色块，左上三角代表亲吻、右下三角代表露点，有色表示该章有对应记录。
  • 点击章节色块或切换到详细模式，可查看该章亲吻 / 露点的完整文字记录。

内容边界（重要）

  • 允许：漫画封面图、章节号、角色名、文字描述。
  • 不允许：具体场景图片、漫画资源链接、下载链接、图床外链、露点截图。
  • 露点场景只描述“哪个章节、什么情境、什么镜头角度”，不配图。
  • 佐证图片只存在于你的邮箱/表单服务后台，绝不放入仓库。

本地预览

直接双击 index.html 即可预览；数据以 JS 文件加载，无需构建。

# 或使用任意静态服务器
python -m http.server 8080
# 打开 http://localhost:8080
